# Барбершоп: сайт с онлайн-записью + CRM

Дизайн-документ проекта. Источник правды для архитектуры, модели данных и порядка работ.
Схема БД: `prisma/schema.prisma`. Защита от пересечения записей: миграция `booking_no_overlap` (см. раздел 5.3).

---

## 1. Цель

Портфолио-проект фуллстек-разработчика, который должен выглядеть и работать как реальный коммерческий продукт:

- **Публичный сайт** барбершопа: услуги, мастера, онлайн-запись в несколько шагов.
- **CRM / админка** для владельца и персонала: расписание, записи, клиентская база, аналитика.
- **Продакшен-деплой**: свой домен, HTTPS, CI/CD, бэкапы.

Критерий успеха: заказчик открывает демо с телефона, записывается за минуту, заходит в админку по демо-доступу и видит «живые» графики и клиентов.

### 1.1. Входит в MVP

- Запись с сайта: услуга(и) → мастер (или «любой») → дата → время → контакты → подтверждение.
- Расчёт свободных слотов с учётом рабочих часов, перерывов, отпусков и существующих записей.
- Защита от двойной записи на уровне БД.
- Уведомления персоналу в Telegram о новых записях и отменах.
- Админка: календарь записей, управление статусами, ручное создание записи (телефон, «с улицы»).
- CRM: карточка клиента с историей, заметками и тегами; поиск и фильтры.
- Справочники: услуги, мастера, график работы, отпуска.
- Аналитика для владельца (раздел 8).
- Сид-данные для демо и демо-вход.

### 1.2. Не входит в MVP (фаза 2)

- Онлайн-оплата, предоплата.
- Напоминания клиентам в Telegram (нужна привязка бота к клиенту).
- Отмена или перенос записи самим клиентом по ссылке.
- Программа лояльности, абонементы, сертификаты.
- Несколько филиалов.

## 2. Стек

| Слой | Технология |
|---|---|
| Фреймворк | Next.js (App Router), React, TypeScript (strict) |
| БД | PostgreSQL 16 |
| ORM | Prisma |
| Авторизация | Better Auth: email + пароль, роль в `User.role` |
| UI | Tailwind CSS + shadcn/ui |
| Формы | React Hook Form + Zod (одни и те же схемы на клиенте и сервере) |
| Таблицы | TanStack Table |
| Графики | Recharts |
| Даты | date-fns + date-fns-tz |
| Уведомления | Telegram Bot API (прямые HTTP-запросы, без библиотек) |
| Тесты | Vitest (юнит), Playwright (e2e) |
| Деплой | Docker, docker-compose, Caddy, GitHub Actions, VPS |

Принципы:
- Монолит на Next.js. Отдельный бэкенд не нужен.
- Чтение данных выполняется в Server Components, мутации в Server Actions, вебхуки и cron-эндпоинты в Route Handlers.
- Вся бизнес-логика лежит в `src/server/`, а не в компонентах. Компоненты только вызывают функции сервисного слоя.

## 5. Модель данных

Полная схема лежит в `prisma/schema.prisma`. Ниже ключевые сущности и инварианты.

### 5.1. Сущности

- **User**: сотрудник с доступом в админку (OWNER / ADMIN / MASTER).
- **Master**: мастер. Может быть связан с `User`, если у мастера есть вход.
- **Service**: услуга с базовой ценой и длительностью.
- **MasterService**: какие услуги делает мастер, с переопределением цены и длительности.
- **WorkingHours**: недельный график, интервалы в минутах от полуночи. Несколько интервалов в день означают смену с перерывом.
- **TimeOff**: отпуск, больничный или разовый перерыв (конкретные даты и время).
- **Client**: клиент. Аккаунта нет, уникальный ключ — нормализованный телефон.
- **Booking**: запись (клиент, мастер, интервал `[startsAt, endsAt)`, статус, источник, итоговая цена).
- **BookingItem**: услуги в записи со **снимком** цены и длительности на момент записи.
- **Payment**: оплата по записи (наличные, карта, онлайн).

### 5.2. Инварианты

1. Деньги хранятся в **копейках** (`Int`). Форматирование только в `lib/money.ts`.
2. Время хранится в `timestamptz` (UTC). Отображение и расчёт слотов ведутся в таймзоне салона (`config/salon.ts`, по умолчанию `Europe/Moscow`).
3. `Booking.endsAt = startsAt + Σ BookingItem.durationMin`.
4. `Booking.totalPrice = Σ BookingItem.price`. Цена и длительность **всегда пересчитываются на сервере**, данным с клиента не доверяем.
5. Изменение прайса не меняет существующие записи: в них хранятся снимки.
6. Телефон хранится только в формате E.164 (`+79991234567`).
7. Активные статусы, которые занимают время мастера: `PENDING`, `CONFIRMED`, `COMPLETED`.

### 5.3. Защита от пересечений

Prisma не поддерживает exclusion constraints, поэтому нужна ручная миграция:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE "Booking"
  ADD CONSTRAINT booking_no_overlap
  EXCLUDE USING gist (
    "masterId" WITH =,
    tstzrange("startsAt", "endsAt", '[)') WITH &&
  )
  WHERE (status IN ('PENDING', 'CONFIRMED', 'COMPLETED'));
```

Создание: `npx prisma migrate dev --create-only --name booking_no_overlap`, вставить SQL, применить.
При конфликте Postgres возвращает код `23P01`. Сервисный слой превращает его в доменную ошибку `SlotTakenError`.

### 5.4. Изменения схемы относительно исходной версии

- Таблицы авторизации добавляются по инструкции выбранной библиотеки (Better Auth генерирует их сам).
- `Booking.notifiedAt DateTime?` хранит время отправки уведомления персоналу, чтобы не отправлять дважды.

## 6. Расчёт свободных слотов

Самая важная бизнес-логика. Реализуется как **чистая функция** без обращений к БД, полностью покрыта юнит-тестами.

### 6.1. Настройки (`config/salon.ts`)

```ts
export const salon = {
  timezone: "Europe/Moscow",
  slotStepMin: 15,        // шаг сетки времени
  minLeadTimeMin: 60,     // нельзя записаться ближе чем за час
  bookingHorizonDays: 30, // запись максимум на 30 дней вперёд
};
```

### 6.2. Вход и выход

```ts
type Interval = { start: Date; end: Date }; // полуинтервал [start, end)

function getAvailableSlots(input: {
  date: string;              // "2026-11-03", дата в таймзоне салона
  durationMin: number;       // суммарная длительность выбранных услуг для этого мастера
  workingHours: { startMin: number; endMin: number }[]; // интервалы на этот день недели
  timeOffs: Interval[];
  bookings: Interval[];      // активные записи мастера, пересекающие этот день
  now: Date;
  settings: typeof salon;
}): Date[]                   // время начала доступных слотов (UTC)
```

### 6.3. Алгоритм

1. Перевести `workingHours` дня в абсолютные интервалы с учётом таймзоны салона (корректно обрабатывать переходы на летнее время, даже если в РФ их сейчас нет).
2. Вычесть из рабочих интервалов `timeOffs` и `bookings` и получить список свободных интервалов.
3. Отсечь всё, что раньше `now + minLeadTimeMin`.
4. В каждом свободном интервале перебрать кандидаты начала с шагом `slotStepMin`, выровненные по сетке от начала часа. Кандидат подходит, если `start + durationMin <= interval.end`.
5. Вернуть отсортированный список.

Если дата за пределами `bookingHorizonDays` или в прошлом, вернуть пустой список.

### 6.4. «Любой мастер»

Посчитать слоты для каждого мастера, который делает **все** выбранные услуги (длительность у каждого своя), и объединить. При создании записи мастер выбирается среди свободных в это время, с наименьшей загрузкой за день.

### 6.5. Обязательные тест-кейсы

- Пустой график → нет слотов.
- Смена с перерывом: слот не пересекает перерыв.
- Услуга длиннее свободного окна → слот не предлагается.
- Запись вплотную к другой (`end == start`) допустима.
- Отпуск на весь день и частичный перерыв.
- `minLeadTimeMin`: сегодня утром нет слотов, которые уже прошли или наступают меньше чем через час.
- Граница суток и таймзона: записи, созданные в UTC, корректно влияют на сетку по Москве.

## 7. Процесс записи

### 7.1. Шаги на сайте (`/book`)

1. **Услуги**: можно выбрать несколько. Показываются цена «от» и длительность.
2. **Мастер**: только те, кто делает все выбранные услуги, плюс вариант «Любой мастер». Цена и длительность пересчитываются под мастера.
3. **Дата**: календарь на `bookingHorizonDays`. Дни без слотов неактивны.
4. **Время**: сетка слотов.
5. **Контакты**: имя, телефон (маска), комментарий, согласие на обработку данных.
6. **Подтверждение** → `/book/success` со сводкой и кнопкой «Добавить в календарь» (.ics).

Состояние мастера записи хранится в URL search params, чтобы ссылку можно было переслать, а кнопка «назад» работала.

### 7.2. Server Action `createBooking`

1. Валидация Zod-схемой.
2. Антиспам: honeypot-поле, лимит запросов по IP (например, 5 в 10 минут).
3. Нормализация телефона, upsert `Client` по телефону (имя обновляется, только если было пустым).
4. Загрузка услуг и `MasterService`, пересчёт цены и длительности **на сервере**.
5. Повторная проверка слота через `getAvailableSlots` (быстрый отказ с понятной ошибкой).
6. В транзакции: создать `Booking` + `BookingItem[]`.
7. Ловить `23P01` → `SlotTakenError` → в UI показать «Это время только что заняли» и обновить слоты.
8. После коммита отправить уведомление в Telegram. Ошибка отправки не должна ломать запись: залогировать и выставить `notifiedAt = null`, cron отправит повторно.

### 7.3. Жизненный цикл статуса

```
PENDING → CONFIRMED → COMPLETED
   ↓          ↓
CANCELLED  CANCELLED / NO_SHOW
```

- Перевод в `COMPLETED` предлагает сразу внести оплату (`Payment`).
- `CANCELLED` выставляет `cancelledAt` и освобождает слот (constraint его больше не учитывает).

## 8. CRM и аналитика

### 8.1. Карточка клиента

Контакты, теги, заметки, список визитов, сумма за всё время, средний чек, дата последнего визита, любимый мастер, процент неявок.

### 8.2. Список клиентов

Поиск по имени и телефону; фильтры по тегам, мастеру, «давно не был», «новые за период». Серверная пагинация.

### 8.3. Метрики (страница `/admin/analytics`, выбор периода)

| Метрика | Определение |
|---|---|
| Выручка | Σ `Payment.amount` за период, разбивка по дням, мастерам, способам оплаты |
| Выручка по услугам | Σ `BookingItem.price` для `COMPLETED` записей |
| Число визитов | количество `COMPLETED` записей |
| Средний чек | выручка / число визитов |
| Загрузка мастера | занятые минуты активных записей / рабочие минуты по графику за вычетом `TimeOff` |
| Неявки | `NO_SHOW` / (`COMPLETED` + `NO_SHOW`) |
| Повторные клиенты | доля клиентов периода, у которых до начала периода уже был `COMPLETED` визит |
| Новые клиенты | клиенты, чей первый `COMPLETED` визит попал в период |
| «Спящие» клиенты | последний `COMPLETED` визит больше 45 дней назад, будущих записей нет |
| Источники | распределение записей по `source` |

Агрегации выполняются SQL-запросами (Prisma `groupBy` или `$queryRaw` для сложных), а не перебором в JS. Функции лежат в `src/server/analytics/`, каждая с типизированным результатом.

### 8.4. Экран «Сегодня» (`/admin`)

Записи на сегодня по мастерам, ближайшая запись, кнопки быстрой смены статуса, выручка дня.

## 9. Уведомления

- Персоналу в Telegram-чат салона (`TELEGRAM_CHAT_ID`): новая запись, отмена.
- Формат: клиент, телефон, услуги, мастер, дата и время, ссылка на запись в админке.
- `GET /api/cron/daily?secret=...` повторно отправляет неотправленные уведомления (`notifiedAt IS NULL`). Вызывается cron-контейнером или системным cron на VPS.

## 10. Безопасность

- RBAC-проверка в каждом Server Action (раздел 4).
- Все входные данные проходят через Zod.
- Лимит запросов и honeypot на публичной записи.
- Секреты только в env, `.env.example` в репозитории.
- Пароли хэшируются средствами библиотеки авторизации.
- Персональные данные клиентов не логируются.
- Заголовки безопасности (CSP, HSTS через Caddy).

## 13. Сид-данные для демо

`prisma/seed.ts` создаёт:
- пользователей: `owner@demo.ru`, `admin@demo.ru`, `master@demo.ru` (пароли из env);
- 4 мастеров с разными графиками и одним отпуском;
- 10 услуг (стрижки, борода, комплексы, окрашивание);
- около 200 клиентов с реалистичными именами, тегами и заметками;
- записи за последние 90 дней и на 14 дней вперёд со смесью статусов, примерно 8% неявок, и оплатами.

Сид должен быть **детерминированным** (фиксированный seed генератора), чтобы демо выглядело одинаково после каждого пересоздания БД.
На странице логина показывается блок «Демо-доступ» с логинами.

## 14. Тестирование

- **Юнит (Vitest)**: `getAvailableSlots` (все кейсы из 6.5), нормализация телефона, расчёт цены и длительности, функции метрик на фиксированных данных.
- **Интеграционные**: `createBooking` на тестовой БД, включая гонку двух параллельных записей на один слот (ровно одна успешна).
- **E2E (Playwright)**: полный путь записи с телефона; вход в админку и смена статуса.

## 15. Этапы работ

Каждый этап заканчивается зелёными `lint`, `typecheck` и тестами, а также коммитом.

1. **Каркас.** Next.js + TS strict, Tailwind, shadcn/ui, Prisma, docker-compose с Postgres, `.env.example`, ESLint/Prettier.
2. **Схема БД.** `schema.prisma`, миграции, constraint из 5.3, сид-данные.
3. **Авторизация.** Логин, `requireRole`, защищённый layout админки.
4. **Справочники.** CRUD услуг, мастеров, графика, отпусков.
5. **Слоты.** `getAvailableSlots` + юнит-тесты (сначала тесты).
6. **Запись с сайта.** Мастер записи, `createBooking`, Telegram-уведомление.
7. **Админка записей.** Экран «Сегодня», календарь, список, смена статусов, ручная запись, оплаты.
8. **CRM.** Список и карточка клиента, теги, заметки.
9. **Аналитика.** Метрики из 8.3, графики.
10. **Публичный сайт.** Главная, услуги, мастера, SEO.
11. **Деплой.** Dockerfile, Caddy, GitHub Actions, бэкапы, домен.
12. **Полировка.** E2E-тесты, Lighthouse, README со скриншотами и архитектурой.

## 17. Правила для работы с кодом

- TypeScript strict, без `any`.
- Бизнес-логика в `src/server/`, Zod-схемы в `src/lib/validation/`, компоненты без прямых запросов к Prisma.
- Деньги только через `lib/money.ts`, даты только через `lib/time.ts`.
- Новая логика расчётов пишется вместе с тестами.
- Изменения схемы БД делаются только через миграции Prisma. При изменении модели обновлять раздел 5 этого документа.
- Интерфейс и сообщения пользователю на русском, код и названия сущностей на английском.
