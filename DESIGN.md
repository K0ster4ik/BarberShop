# Барбершоп: сайт с онлайн-записью + CRM

Дизайн-документ проекта. Источник правды для архитектуры, модели данных и порядка работ.
Схема БД: `prisma/schema.prisma`. Защита от пересечения записей: миграция `booking_no_overlap` (см. раздел 5.3).

---

## 1. Цель

Портфолио-проект фуллстек-разработчика, который должен выглядеть и работать как реальный коммерческий продукт. Реального салона за ним нет, это **публичное демо**.

- **Публичный сайт** барбершопа: услуги, мастера, онлайн-запись в несколько шагов. Открыт всем: любой посетитель может записаться как настоящий клиент.
- **CRM / админка** для владельца и персонала: расписание, записи, клиентская база, скидки, аналитика. Закрыта паролями, доступы к ролям OWNER / ADMIN / MASTER выдаются вручную тем, кому нужен полный демо-доступ.
- **Публичный Telegram-канал**, куда приходят заявки с сайта: посетитель записывается и сразу видит своё уведомление.
- **Продакшен-деплой**: свой домен, HTTPS, CI/CD, бэкапы.
- **Сброс демо**: раз в час данные возвращаются к исходному состоянию, чтобы мусор от посетителей не копился (раздел 13).

Критерий успеха: заказчик открывает демо с телефона, записывается за минуту, видит уведомление в канале, заходит в админку по выданному доступу и видит «живые» графики и клиентов.

### 1.1. Входит в MVP

- Запись с сайта: услуга(и) → мастер (или «любой») → дата → время → контакты (+ промокод) → подтверждение.
- Расчёт свободных слотов с учётом рабочих часов, перерывов, отпусков, буфера на уборку и существующих записей.
- Защита от двойной записи на уровне БД.
- Отмена записи клиентом по ссылке из подтверждения.
- Уведомления о заявках с сайта и их отменах в публичный Telegram-канал.
- Админка: календарь записей, управление статусами, ручное создание записи (телефон, «с улицы»), перенос, изменение длительности, ручная правка цены, оплаты.
- Скидки: акции мастеров, промокоды, постоянная скидка клиента, ручная скидка (раздел 7.3).
- CRM: карточка клиента с историей, заметками и тегами; поиск и фильтры.
- Справочники: категории, услуги, мастера и их цены, график работы, отпуска.
- Аналитика для владельца и личная выручка мастера (раздел 8).
- Сид-данные и ежечасный сброс демо.
- Страница политики обработки персональных данных.

### 1.2. Не входит в MVP (фаза 2)

- Онлайн-оплата, предоплата.
- Напоминания клиентам в Telegram (нужна привязка бота к клиенту).
- Перенос записи самим клиентом.
- Перетаскивание записей мышкой в календаре (в MVP перенос и длительность меняются через форму).
- Программа лояльности, абонементы, сертификаты.
- Несколько филиалов.

## 2. Стек

| Слой | Технология |
|---|---|
| Фреймворк | Next.js 16 (App Router), React, TypeScript (strict) |
| БД | PostgreSQL 16 |
| ORM | Prisma 7 + `@prisma/adapter-pg` |
| Авторизация | Better Auth: email + пароль, самостоятельная регистрация выключена, роль в `User.role` |
| UI | Tailwind CSS 4 + shadcn/ui |
| Формы | React Hook Form + Zod (одни и те же схемы на клиенте и сервере) |
| Таблицы | TanStack Table |
| Графики | Recharts |
| Даты | date-fns + date-fns-tz |
| Телефоны | libphonenumber-js (номера любых стран) |
| Уведомления | Telegram Bot API (прямые HTTP-запросы, без библиотек) |
| Тесты | Vitest (юнит и интеграционные), Playwright (e2e) |
| Деплой | Docker, docker-compose, Caddy, GitHub Actions, VPS |
| Пакетный менеджер | npm |

Принципы:
- Монолит на Next.js. Отдельный бэкенд не нужен.
- Чтение данных выполняется в Server Components, мутации в Server Actions, вебхуки и cron-эндпоинты в Route Handlers.
- Вся бизнес-логика лежит в `src/server/`, а не в компонентах. Компоненты только вызывают функции сервисного слоя.

## 4. Роли и доступ

| Действие | OWNER | ADMIN | MASTER | Гость |
|---|:-:|:-:|:-:|:-:|
| Записаться с сайта, отменить свою запись по ссылке | — | — | — | ✅ |
| Видеть записи | ✅ все | ✅ все | только свои | — |
| Создавать, переносить, менять цену и длительность записей | ✅ | ✅ | — | — |
| Менять статус записи | ✅ | ✅ | только своих | — |
| Удалять записи (мягко) | ✅ | ✅ | — | — |
| Клиентская база | ✅ | ✅ | только клиенты своих записей | — |
| Постоянная скидка клиента | ✅ | ✅ | — | — |
| Услуги и категории | ✅ | ✅ | — | — |
| Профиль и фото мастера, добавление мастеров | ✅ | ✅ | только просмотр своего | — |
| Цены мастера, его акции, график, отпуска | ✅ всех | ✅ всех | только свои | — |
| Промокоды | ✅ | ✅ | — | — |
| Аналитика и выручка салона | ✅ | — | — | — |
| Выручка по своим записям | ✅ | — | ✅ | — |
| Управление пользователями | ✅ | — | — | — |

Правила:
- **Каждый** Server Action и Route Handler начинается с проверки доступа. Скрытие кнопок в UI защитой не считается.
- Для персонала это `requireRole(...)`, а для MASTER ещё и проверка владения: запись, клиент или настройки принадлежат именно его `Master`. Проверка делается в сервисном слое, а не только в UI.
- Исключения из `requireRole`: публичный `createBooking` и отмена по токену (защищены лимитом запросов), `api/auth` (сама библиотека), `api/cron/*` (секрет в заголовке `Authorization: Bearer`).

Как это устроено (`src/server/auth/`):

| Уровень | Что делает |
|---|---|
| `proxy.ts` | Без cookie сессии сразу редиректит `/admin/*` на `/admin/login?next=…`. Это оптимизация, а не защита: подделанную cookie он пропустит. |
| `getCurrentStaff()` | Читает сессию Better Auth, отсекает отключённых (`isActive = false`), для MASTER подтягивает `masterId`. Помечена `use cache: private`: layout и страница одного запроса делят один поход в БД, а на сервере между запросами ничего не кэшируется. Только в `next dev` Next.js держит результат в памяти и один раз отдаёт старый, пока считает новый: после смены роли первая загрузка страницы может показать прежнюю роль. Server Actions проверяют роль заново, а в production такого кэша нет. |
| `requireRole(...roles)` | Для страниц и Server Actions: нет сессии → `/admin/login`, нет роли → `forbidden()` (403, `forbidden.tsx`). MASTER без привязанной карточки мастера не проходит ни в один раздел. |
| `SECTION_ROLES` | Кто открывает какой раздел. Из этой таблицы строятся и меню, и проверки на страницах, поэтому они не разойдутся. |
| `assertOwnMaster`, `bookingScope`, `clientScope`, `masterScope` | Проверка владения для MASTER в сервисном слое. Фильтры подмешиваются в `where`, поэтому MASTER физически не получает чужие строки. |

Шаблон страниц админки: `page.tsx` синхронный и возвращает `<Suspense fallback={<PageSkeleton/>}>` вокруг компонента, который вызывает `requireRole` и грузит данные (для заглушек — `<RoleGate>`). `requireRole` вызывает `connection()`: всё за проверкой роли рендерится в момент запроса. Без этого шаблона проверка «мгновенной навигации» Cache Components считает страницу блокирующей. `loading.tsx` остаётся запасной границей.

Server Actions справочников: `requireRole` — до `runAction` (его `redirect`/`forbidden` должны дойти до Next.js), затем Zod-схема, сервис, `refresh()`. `runAction` превращает `DomainError`, `ForbiddenError`, ошибки Zod и нарушения уникальности в ответ `{ ok: false, error, fieldErrors }`, который форма раскладывает по полям.

Better Auth: регистрация выключена, сотрудников создаёт OWNER. HTTP-эндпоинты, которые приложению не нужны (`/update-user`, `/change-email`, восстановление пароля по почте, OAuth), отключены через `disabledPaths`. HTTP-вход (`/sign-in/email`) тоже закрыт: вход идёт только через Server Action с собственным лимитом попыток, иначе этот лимит можно было бы обойти прямыми запросами. `disabledPaths` действует только на HTTP-роутер, серверный `auth.api.signInEmail` работает. Роль и `isActive` нельзя передать с клиента (`input: false`). Отключённый сотрудник не получает новую сессию (хук `session.create.before`).

## 5. Модель данных

Полная схема лежит в `prisma/schema.prisma`. Ниже ключевые сущности и инварианты.

### 5.1. Сущности

- **User**: сотрудник с доступом в админку (OWNER / ADMIN / MASTER). Таблицы `Session`, `Account`, `Verification` генерирует Better Auth.
- **Master**: мастер (имя, должность, описание). Может быть связан с `User`, если у мастера есть вход. Фото лежит в volume `uploads`, в БД хранится путь.
- **ServiceCategory**: категория услуг (стрижки, борода, комплексы, окрашивание), порядок отображения.
- **Service**: услуга с категорией, рекомендуемой ценой и длительностью, опциональным буфером на уборку.
- **MasterService**: какие услуги делает мастер, **его цена** и длительность. При добавлении услуги мастеру заполняются значениями из `Service`, дальше мастер меняет их сам.
- **MasterPromotion**: акция мастера. Её создаёт сам мастер или админ. Привязана к мастеру, опционально к услуге (если услуги нет, действует на все услуги мастера), задаётся процентом или суммой, может быть ограничена периодом `[validFrom, validUntil)`.
- **PromoCode**: промокод салона: процент или сумма, срок действия, лимит использований.
- **WorkingHours**: недельный график, интервалы в минутах от полуночи. Несколько интервалов в день означают смену с перерывом.
- **TimeOff**: отпуск, больничный или разовый перерыв (конкретные даты и время). В интерфейсе — «отсутствие»: одно слово для всех трёх случаев. Время частичного отсутствия — с шагом 5 минут, как в графике.
- **Client**: клиент. Аккаунта нет, уникальный ключ — нормализованный телефон. Необязательные email и дата рождения. Может иметь постоянную скидку (процент или сумма).
- **Tag** + **ClientTag**: теги клиентов с цветом бейджа, связь многие-ко-многим (для фильтров в CRM).
- **ClientNote**: заметки персонала о клиенте с автором и временем.
- **Booking**: запись (клиент, мастер, `[startsAt, endsAt)`, буфер, статус, источник, цены и скидка салона, токен отмены).
- **BookingItem**: услуги в записи со **снимком** цены мастера, скидки мастера и длительности на момент записи.
- **Payment**: оплата по записи (наличные, карта, онлайн). У записи может быть несколько оплат, например часть наличными, часть картой.
- **Notification**: очередь исходящих уведомлений (outbox), раздел 9.

Перечисления:
- `Role`: `OWNER`, `ADMIN`, `MASTER`.
- `BookingStatus`: `PENDING`, `CONFIRMED`, `COMPLETED`, `CANCELLED`, `NO_SHOW`.
- `BookingSource`: `WEBSITE`, `PHONE`, `WALK_IN`.
- `DiscountKind`: `PERCENT`, `AMOUNT`.
- `SalonDiscountSource`: `PROMO_CODE`, `CLIENT`, `MANUAL`.
- `CancelledBy`: `CLIENT`, `STAFF`.
- `PaymentMethod`: `CASH`, `CARD`, `ONLINE`.

### 5.2. Инварианты

1. Деньги хранятся в **копейках** (`Int`). Форматирование и округление только в `lib/money.ts`.
2. Время хранится в `timestamptz` (UTC). Отображение и расчёт слотов ведутся в таймзоне салона (`config/salon.ts`, по умолчанию `Europe/Moscow`).
3. `Booking.durationMin = Σ BookingItem.durationMin`, если админ не задал длительность вручную (`isDurationManual`). `endsAt = startsAt + durationMin`.
4. `Booking.blockedUntil = endsAt + bufferMin`. Буфер берётся из услуг записи (максимальный) или из настроек салона.
5. `BookingItem.price = basePrice − masterDiscount`, если цена не задана админом вручную (`isPriceManual`).
6. `Booking.subtotal = Σ BookingItem.price`, `Booking.totalPrice = subtotal − salonDiscount`, итог не меньше нуля.
7. Цены, скидки и длительность **всегда считаются на сервере**. Данным с клиента не доверяем. Ручные правки принимаются только от OWNER / ADMIN.
8. Изменение прайса и акций не меняет существующие записи: в них хранятся снимки.
9. Телефон хранится только в формате E.164 (`+79991234567`, `+491511234567`).
10. Активные статусы, которые занимают время мастера: `PENDING`, `CONFIRMED`, `COMPLETED`. Мягко удалённые записи (`deletedAt IS NOT NULL`) время не занимают и нигде не учитываются.
11. Токен отмены хранится только в виде SHA-256 хэша (`cancelTokenHash`).

### 5.3. Защита от пересечений

Prisma не поддерживает exclusion constraints, поэтому нужна ручная миграция. Интервал берётся вместе с буфером: следующая запись может начаться не раньше `blockedUntil` предыдущей.

`blockedUntil` хранится отдельной колонкой, а не вычисляется в constraint: выражение `timestamptz + interval` не `IMMUTABLE`, и Postgres не разрешит его в индексе.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE "Booking"
  ADD CONSTRAINT booking_no_overlap
  EXCLUDE USING gist (
    "masterId" WITH =,
    tstzrange("startsAt", "blockedUntil", '[)') WITH &&
  )
  WHERE (status IN ('PENDING', 'CONFIRMED', 'COMPLETED') AND "deletedAt" IS NULL);
```

Создание: `npx prisma migrate dev --create-only --name booking_no_overlap`, вставить SQL, применить.

При конфликте Postgres возвращает код `23P01`. Prisma 7 с `@prisma/adapter-pg` отдаёт его как `PrismaClientKnownRequestError` с кодом `P2039`, а исходный SQLSTATE и текст ошибки лежат в `meta.driverAdapterError.cause`. Распознаёт его `isBookingOverlapError` (`src/server/bookings/errors.ts`). Сервисный слой превращает ошибку в доменную `SlotTakenError`. Поведение закреплено интеграционными тестами, включая гонку двух параллельных записей.

Остальные инварианты, которые нельзя выразить в `schema.prisma`, закреплены CHECK-ограничениями в миграции `integrity_checks`: корректные интервалы записей, отпусков и графика, неотрицательные суммы, процент скидки 1..100, промокод в верхнем регистре, телефон в E.164, `CANCELLED` ⇔ `cancelledAt`. Сервисный слой проверяет то же самое с понятными сообщениями, а CHECK — последняя линия защиты.

Prisma не видит эти ограничения как расхождение со схемой: `migrate dev` после них генерирует пустую миграцию.

## 6. Расчёт свободных слотов

Самая важная бизнес-логика. Реализуется как **чистая функция** без обращений к БД, полностью покрыта юнит-тестами.

### 6.1. Настройки (`config/salon.ts`)

```ts
export const salon = {
  timezone: "Europe/Moscow",
  slotStepMin: 15,             // шаг сетки времени, должен делить 30 минут
  defaultBufferMin: 10,        // уборка после записи, если у услуги не задан свой буфер
  minLeadTimeMin: 60,          // нельзя записаться ближе чем за час
  bookingHorizonDays: 30,      // запись на 30 дней, считая сегодняшний
  clientCancelLeadTimeMin: 120, // клиент может отменить запись не позже чем за 2 часа
} as const satisfies SalonSettings;
```

Тип `SalonSettings` общий (строки и числа), поэтому функции расчёта принимают любые настройки, а тесты проверяют другие таймзоны и шаг сетки.

### 6.2. Вход и выход

```ts
type Interval = { start: Date; end: Date }; // полуинтервал [start, end)

function getAvailableSlots(input: {
  date: string;              // "2026-11-03", дата в таймзоне салона
  durationMin: number;       // суммарная длительность выбранных услуг для этого мастера
  bufferMin: number;         // буфер после записи
  workingHours: { startMin: number; endMin: number }[]; // интервалы на этот день недели
  timeOffs: Interval[];
  bookings: Interval[];      // активные записи мастера [startsAt, blockedUntil), пересекающие этот день
  now: Date;
  settings: Pick<SalonSettings, "timezone" | "slotStepMin" | "minLeadTimeMin" | "bookingHorizonDays">;
}): Date[]                   // время начала доступных слотов (UTC), по возрастанию, без повторов
```

Данные дня берёт `loadMasterDays(db, masterIds, date)` (`slots/load.ts`): график на день недели, отсутствия и активные записи, пересекающие день, с запасом в сутки после него (уборка последней записи может уйти за полночь). Там же считаются занятые минуты за день (`bookedMin`) для выбора «любого мастера».

### 6.3. Алгоритм

1. Перевести `workingHours` дня в абсолютные интервалы с учётом таймзоны салона (корректно обрабатывать переходы на летнее время, даже если в РФ их сейчас нет). Соприкасающиеся интервалы (10–12 и 12–14) склеиваются в одну смену. Время из пропущенного часа (02:30 при переводе часов 02:00 → 03:00) читается со смещением до перехода, как в RFC 5545 и Temporal, и становится 03:30 — смена не начинается раньше графика. В повторяющийся час при переводе назад берётся второе, зимнее, время.
2. Вычесть из рабочих интервалов `timeOffs` и `bookings` и получить список свободных интервалов.
3. Кандидаты начала в каждом свободном интервале:
   - точки сетки с шагом `slotStepMin`, отсчитанные от полуночи по часам салона (а не от эпохи UTC: в поясах вроде UTC+5:30 часовая сетка иначе съехала бы на полчаса);
   - начало самого свободного интервала (конец предыдущей записи с буфером, конец перерыва). Так записи нестандартной длины не оставляют «дыр» в расписании.
4. Кандидат подходит, если:
   - `start >= now + minLeadTimeMin` (отсечка по времени не создаёт новых кандидатов);
   - `start + durationMin <= interval.end`;
   - `[start, start + durationMin + bufferMin)` не пересекается ни с одной записью и ни с одним отсутствием. Конец рабочего интервала (закрытие или обед по графику) буфер пересекать может: уборка после закрытия или перед обедом допустима. Так же проверяются и записи, которые админ поставил вне графика.
5. Вернуть отсортированный список без дубликатов.

Если дата за пределами `bookingHorizonDays` или в прошлом, вернуть пустой список.

### 6.4. «Любой мастер»

Посчитать слоты для каждого мастера, который делает **все** выбранные услуги (длительность у каждого своя), и объединить.

- На шагах до выбора времени клиент видит диапазон цен «от–до» по подходящим мастерам.
- При выборе времени мастер назначается среди свободных в это время, с наименьшей загрузкой за день. На шаге подтверждения клиент видит конкретного мастера и точную цену. Слоты объединяет `combineMasterSlots` (`slots/any-master.ts`): для каждого времени — список свободных мастеров от наименее загруженного; при равной загрузке сохраняется исходный порядок.
- Если при создании записи назначенный мастер уже занят (`SlotTakenError`), сервер пробует следующего свободного. Если цена у него другая, клиент возвращается на подтверждение с новой ценой. Если свободных нет, показывается «Это время только что заняли».

### 6.5. Обязательные тест-кейсы

- Пустой график → нет слотов.
- Смена с перерывом: слот не пересекает перерыв.
- Услуга длиннее свободного окна → слот не предлагается.
- Запись вплотную к чужому буферу (`blockedUntil == start`) допустима, внутрь буфера — нет.
- Буфер новой записи не должен залезать на следующую запись, но может выходить за конец смены.
- Запись нестандартной длины: следующий слот предлагается сразу после её буфера, а не только по сетке.
- Отпуск на весь день и частичный перерыв.
- `minLeadTimeMin`: сегодня утром нет слотов, которые уже прошли или наступают меньше чем через час; отсечка не создаёт «кривых» кандидатов вроде 11:37.
- Граница суток и таймзона: записи, созданные в UTC, корректно влияют на сетку по Москве.

## 7. Процесс записи

### 7.1. Шаги на сайте (`/book`)

Четыре экрана (решение 2026-10-28: дата и время — один экран, контакты и подтверждение — тоже):

1. **Услуги**, сгруппированные по категориям: можно выбрать несколько (до 5). Показываются цена «от» и длительность.
2. **Мастер**: только те, кто делает все выбранные услуги, плюс вариант «Любой мастер» с диапазоном цен. Цены и длительность пересчитываются под мастера, акции мастера видны (старая цена зачёркнута).
3. **Дата и время**: календарь на `bookingHorizonDays`, дни без слотов неактивны; под ним — свободное время дня, сгруппированное «Утро / День / Вечер».
4. **Контакты и подтверждение**: мастер (для «любого» — уже назначенный), время, услуги и цена; имя, телефон (страна + номер, любой страны), комментарий, промокод, согласие со ссылкой на `/privacy`. Цена пересчитывается, когда введён телефон (постоянная скидка клиента) или применён промокод. «Записаться» → редирект на `/booking/[token]`.

На десктопе справа — сводка «Ваша запись» с кнопкой, на телефоне — панель, закреплённая снизу. Визуальное направление — «Тёмный премиум» и его светлая вариация (`docs/design/`), тема — как в системе, с переключателем.

Страница `/booking/[token]` показывает сводку, кнопку «Добавить в календарь» (.ics) и кнопку «Отменить запись». Ссылка на неё есть и в описании события .ics.

Состояние мастера записи хранится в URL search params (`step`, `services`, `master`, `date`, `time`), чтобы ссылку можно было переслать, а кнопка «назад» работала. Выбор услуг и дня пишется в адрес сразу (`history.replaceState`, без запроса к серверу), а начальное состояние шагов берётся из текущего адреса: при «назад» Next.js показывает страницу из своей истории со старыми пропсами. Шаг не может обогнать данные: без мастера адрес с `step=contacts` откроет шаг мастера; прошедшая дата или дата за горизонтом дают понятное сообщение.

Контакты в адрес не попадают. Имя, страна, телефон и комментарий живут в `sessionStorage` вкладки: если время заняли и клиент вернулся выбрать другое, вводить их заново не нужно. Согласие на обработку данных каждый раз ставится заново.

### 7.2. Server Action `createBooking`

1. Валидация Zod-схемой.
2. Антиспам: honeypot-поле, лимит запросов по IP (5 за 10 минут).
3. Нормализация телефона, upsert `Client` по телефону (имя обновляется, только если было пустым).
4. **Одна активная запись на телефон**: если у клиента уже есть будущая запись в статусе `PENDING` / `CONFIRMED`, отказ с сообщением «На этот номер уже есть активная запись. Отменить её можно по ссылке из подтверждения». Ограничение действует только на запись с сайта: админ может записывать клиента сколько угодно раз.
5. Загрузка услуг, `MasterService`, акций мастера, промокода и скидки клиента; расчёт цены, скидок и длительности **на сервере** через `calculatePricing` (раздел 7.3).
6. Повторная проверка слота через `getAvailableSlots` (быстрый отказ с понятной ошибкой).
7. В транзакции: создать `Booking` + `BookingItem[]` + `Notification`.
8. Ловить `23P01` → `SlotTakenError` → для «любого мастера» попробовать следующего (раздел 6.4), иначе в UI показать «Это время только что заняли» и обновить слоты.
9. После коммита попытаться отправить уведомление сразу. Ошибка отправки не ломает запись: она логируется, уведомление остаётся в очереди, cron повторит.

Новая запись с сайта создаётся в статусе `PENDING`. Подтверждает её мастер или админ.

Детали реализации (`server/bookings/create.ts`):
- Клиент присылает то, что видел на подтверждении: итог, мастера и длительность (`expectedTotal`, `expectedMasterId`, `expectedDurationMin`). Если хоть одно не совпало с расчётом сервера (кончилась акция; для «любого мастера» время досталось другому мастеру — даже с той же ценой), запись не создаётся, а клиент получает новую сводку и объяснение, что изменилось.
- В транзакции берутся `pg_advisory_xact_lock` по телефону (иначе два параллельных запроса прошли бы проверку «одна активная запись») и по промокоду с лимитом (иначе лимит превысился бы на единицу).
- Лимиты по IP: 5 записей, 60 пересчётов цены и 10 отмен за 10 минут. Ловушка для ботов — скрытое поле `website`.
- Уведомление отправляется через `after()` — после ответа клиенту, медленный Telegram запись не задерживает. Отправляется только уведомление этой записи или отмены; старые неудачные повторяет cron.

### 7.3. Цены и скидки

Расчёт выполняет чистая функция `calculatePricing` в `src/server/pricing/`, покрытая юнит-тестами.

Скидка задаётся процентом (`PERCENT`) или суммой (`AMOUNT`). Есть два уровня:

**Скидка мастера** (уровень услуги):
- Источник: акции `MasterPromotion`. Их создаёт сам мастер или админ для конкретного мастера.
- Применяется автоматически к `BookingItem` и видна клиенту на сайте.
- Если к услуге подходит несколько акций, берётся самая выгодная для клиента. Акции не суммируются.
- Период акции проверяется на **момент визита** (`[validFrom, validUntil)`): акция «−20% в ноябре» действует на ноябрьские визиты, когда бы их ни записали.
- **Уменьшает выручку мастера.**

**Скидка салона** (уровень записи):
- Источники: промокод, постоянная скидка клиента, ручная скидка админа.
- Применяется к `subtotal` после скидок мастера.
- Источники не суммируются: из промокода и скидки клиента автоматически берётся больший. При равенстве остаётся скидка клиента, и промокод не расходуется. Ручная скидка админа заменяет автоматическую.
- Промокод проверяется на **момент оформления**: включён, срок начался и не закончился, лимит использований не исчерпан. Если код не применён, `calculatePricing` возвращает причину (`promoCodeIssue`: выключен, ещё не начался, истёк, лимит исчерпан, постоянная скидка не меньше, задана ручная скидка), а интерфейс показывает её текстом из `PROMO_CODE_ISSUE_MESSAGES`.
- **Не уменьшает выручку мастера.**

Округление: сумма скидки округляется до целого рубля в пользу клиента. Цена после скидки не может быть меньше нуля.

Ручная правка админом:
- Цена услуги в записи (`BookingItem.isPriceManual`): заменяет расчётную цену вместе со скидкой мастера (`masterDiscount = 0`, акция не указывается) и считается ценой мастера.
- Длительность записи (`Booking.isDurationManual`): растянуть или сократить с шагом 5 минут. Пересечения по-прежнему проверяет constraint.

### 7.4. Перенос записи админом

Админ меняет время и/или мастера. Если меняется мастер, цены услуг пересчитываются по его прайсу и акциям, кроме цен, заданных вручную. Статус сохраняется. Пересечения проверяет constraint.

### 7.5. Отмена клиентом

- По ссылке `/booking/[token]`. Токен генерируется при создании записи (32 случайных байта, base64url), в БД хранится только хэш.
- Разрешена для `PENDING` / `CONFIRMED`, не позже чем за `clientCancelLeadTimeMin` до начала.
- Выставляет `CANCELLED`, `cancelledAt`, `cancelledBy = CLIENT` и создаёт уведомление об отмене.
- Если запись не найдена (например, демо было сброшено), страница сообщает об этом понятным текстом.
- Отмена — один условный `UPDATE … WHERE status IN (PENDING, CONFIRMED) AND startsAt > now + 2 ч`: два одновременных нажатия не создадут двух уведомлений.
- Токен в адресе — ключ к записи: страница не индексируется (`noindex`) и не отдаёт `Referer`, файл .ics — с `Cache-Control: no-store`. В .ics отменённая запись приходит со `STATUS:CANCELLED`, ожидающая — `TENTATIVE`.

### 7.6. Жизненный цикл статуса

```
PENDING ──→ CONFIRMED ──→ COMPLETED
   │            │
   │            ├──→ CANCELLED
   │            └──→ NO_SHOW
   ├──→ COMPLETED      (мастер забыл подтвердить, а клиент пришёл)
   ├──→ CANCELLED
   └──→ NO_SHOW
```

- `CONFIRMED` выставляет мастер (для своих записей) или админ.
- `COMPLETED` и `NO_SHOW` можно выставить только после `startsAt`.
- Перевод в `COMPLETED` предлагает сразу внести оплату (`Payment`).
- `CANCELLED` выставляет `cancelledAt` и `cancelledBy` и освобождает слот (constraint его больше не учитывает).
- `COMPLETED`, `CANCELLED`, `NO_SHOW` финальные. Ошибочно выставленный `COMPLETED` ↔ `NO_SHOW` админ может исправить.
- **Удаление** (OWNER / ADMIN) мягкое: `deletedAt`. Запись пропадает из интерфейса и аналитики и освобождает слот. Используется для ошибочных записей.

## 8. CRM и аналитика

### 8.1. Карточка клиента

Контакты, теги, заметки, постоянная скидка, список визитов, сумма за всё время, средний чек, дата последнего визита, любимый мастер, процент неявок.

### 8.2. Список клиентов

Поиск по имени и телефону; фильтры по тегам, мастеру, «давно не был», «новые за период». Серверная пагинация.

### 8.3. Метрики (страница `/admin/analytics`, выбор периода)

Период фильтруется по `Booking.startsAt` в таймзоне салона для всех метрик.

| Метрика | Определение |
|---|---|
| Выручка салона | Σ `Payment.amount` по записям периода, разбивка по дням, мастерам, способам оплаты |
| Выручка мастера | Σ `BookingItem.price` (после скидки мастера, до скидки салона) для `COMPLETED` записей мастера |
| Выручка по услугам | Σ `BookingItem.price` для `COMPLETED` записей, по услугам и категориям |
| Скидки | Σ скидок мастеров и Σ `Booking.salonDiscount` по источникам; использование промокодов |
| Неоплаченные визиты | `COMPLETED` записи, где Σ `Payment.amount` < `totalPrice` |
| Число визитов | количество `COMPLETED` записей |
| Средний чек | выручка салона / число визитов |
| Загрузка мастера | занятые минуты активных записей / рабочие минуты по графику за вычетом `TimeOff` |
| Неявки | `NO_SHOW` / (`COMPLETED` + `NO_SHOW`) |
| Повторные клиенты | доля клиентов периода, у которых до начала периода уже был `COMPLETED` визит |
| Новые клиенты | клиенты, чей первый `COMPLETED` визит попал в период |
| «Спящие» клиенты | последний `COMPLETED` визит больше 45 дней назад, будущих записей нет |
| Источники | распределение записей по `source` |

Разница между выручкой мастеров и выручкой салона объясняется скидками салона и неоплаченными визитами. Обе метрики показываются рядом с метрикой «Скидки», чтобы цифры сходились.

**Вид мастера**: MASTER видит ту же страницу, ограниченную своими записями: выручка мастера, число визитов, средний чек, загрузка, неявки. Выручка салона и данные других мастеров ему недоступны.

Агрегации выполняются SQL-запросами (Prisma `groupBy` или `$queryRaw` для сложных), а не перебором в JS. Функции лежат в `src/server/analytics/`, каждая с типизированным результатом.

### 8.4. Экран «Сегодня» (`/admin`)

Записи на сегодня по мастерам, ближайшая запись, кнопки быстрой смены статуса, выручка дня (для MASTER только своя).

## 9. Уведомления

- Получатель: **публичный** Telegram-канал (`TELEGRAM_CHAT_ID`), ссылка на него есть на сайте (`TELEGRAM_CHANNEL_URL`).
- События: новая запись с сайта и её отмена (клиентом или персоналом). Записи, созданные в админке, в канал не отправляются.
- Формат: имя клиента (только первое слово), **маскированный** телефон (`+7 999 *** ** 67`: код страны и первая группа видны, из остального — две последние цифры; если скрытыми осталось бы меньше трёх цифр, как у коротких номеров одной группой `+500 51234`, первая группа тоже скрывается: `+500 ***34`), услуги, мастер, дата и время, итоговая цена. Канал публичный, а посетители могут ввести настоящие данные, поэтому полный телефон в канал не попадает. Текст, который ввёл посетитель, экранируется (`parse_mode=HTML`).
- Механизм — outbox: в той же транзакции, что и запись или отмена, создаётся строка `Notification` (`type`, `bookingId`, `sentAt`, `attempts`, `lastError`). После коммита отправка пробуется сразу.
- `POST /api/cron/notifications` раз в 5 минут повторяет неотправленные (`sentAt IS NULL`, `attempts < 10`) с паузой: после k неудач — не раньше чем через 5·(2^k − 1) минут от создания (5, 15, 35… минут, десятая попытка — примерно через двое суток). Сбой Telegram не сжигает все попытки за час. Секрет — в заголовке `Authorization: Bearer CRON_SECRET`, сравнение за постоянное время.
- Каждое уведомление отправляется в своей транзакции с `SELECT … FOR UPDATE SKIP LOCKED`: если одновременно работают отправка после записи и cron, сообщение не уйдёт дважды. Ошибка Telegram пишется в `lastError` без токена бота.
- Без `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` (локальная разработка) отправка пропускается, уведомления копятся в очереди.
- Сид и сброс демо уведомлений не создают.

## 10. Безопасность

- Проверка доступа в каждом Server Action и Route Handler (раздел 4), включая проверку владения для MASTER.
- Все входные данные проходят через Zod. Переменные окружения валидируются при старте (`src/env.ts`).
- Загрузка фото: только JPEG/PNG/WebP до 5 МБ (лимит тела Server Action — 6 МБ). sharp поворачивает по EXIF, вырезает самый крупный кадр 4:5 (не больше 1200×1500, маленькие снимки не растягиваются) и сохраняет WebP с качеством 90 без метаданных (GPS из фото не утекает). Сохранённый файл — исходник для `next/image`: посетитель получает уменьшенную копию нужной ширины, а высокое качество исходника избавляет от «мыла» двойного сжатия. Имя файла каждый раз новое, раздача с `immutable` и `nosniff`. Путь проверяется по белому списку сегментов `[a-z0-9_-]` с одним расширением — обход каталога невозможен. `next/image` разрешён только для `/uploads/**` без query.
- Лимит запросов (в памяти процесса, одного инстанса достаточно) и honeypot на публичной записи, отмене и проверке промокода. IP берётся из заголовка, который выставляет Caddy; клиентским заголовкам напрямую не доверяем.
- Регистрация в Better Auth выключена, пользователей создаёт OWNER.
- Вход идёт через Server Action, а встроенный лимит Better Auth действует только на его HTTP-эндпоинты. Поэтому у входа свой лимит: 10 попыток за 10 минут с одного IP, а HTTP-вход Better Auth закрыт.
- `safeAdminPath` проверяет параметр `next` после нормализации пути, как это сделает браузер: `/admin/../admin/login` и подобные варианты не дают цикла редиректов и не уводят за пределы `/admin`.
- Next.js в dev-режиме печатает аргументы Server Actions (пароли, телефоны) — это выключено (`logging.serverFunctions: false`).
- Секреты только в env, `.env.example` в репозитории. Секрет cron передаётся в заголовке `Authorization`, а не в URL (URL попадает в логи).
- Пароли хэшируются средствами библиотеки авторизации.
- Персональные данные клиентов не логируются. В публичный канал телефон уходит только маскированным.
- Заголовки безопасности (CSP, HSTS через Caddy).
- **Режим демо** (`DEMO_MODE=true`): демо-пользователям запрещено менять пароль и email, их нельзя удалить. Так один посетитель не закроет доступ остальным.
  - На уровне Better Auth для демо-учёток закрыты `/change-password`, `/list-sessions` и `/revoke-*`: учётки общие, и иначе любой посетитель мог бы выкинуть всех, кто сейчас в них работает. Email и профиль через HTTP не меняются ни у кого (эндпоинты отключены).
  - Управление пользователями в админке проверяет `isDemoUser` в сервисном слое: демо-учётки нельзя отключить, сменить им роль или пароль. Удаления сотрудников нет — только отключение (история записей и заметок сохраняется).
  - Вне демо-режима тоже: владелец не может понизить или отключить себя, и в салоне всегда остаётся хотя бы один активный владелец. Отключение и сброс пароля сразу завершают все сессии сотрудника.
  - Изменения сотрудников идут под `pg_advisory_xact_lock`: иначе два владельца могли бы одновременно отключить друг друга. Карточка мастера привязывается условным `UPDATE … WHERE userId IS NULL`, поэтому два параллельных запроса не получат одну карточку.

## 12. Деплой

### 12.1. Контейнеры (`docker-compose.yml`)

- `app`: Next.js с `output: "standalone"`, многоэтапный Dockerfile.
- `migrate`: отдельная цель Dockerfile с Prisma CLI и миграциями. Запускается разово (`docker compose run --rm migrate`) перед обновлением `app`.
- `db`: Postgres 16, volume для данных, healthcheck.
- `caddy`: reverse proxy с автоматическим HTTPS. Раздаёт `/uploads/*` напрямую из volume `uploads`.
- `cron`: лёгкий контейнер, который дёргает эндпоинты: `/api/cron/notifications` раз в 5 минут, `/api/cron/demo-reset` раз в час.
- `backup`: ежедневный `pg_dump` в volume, хранение 14 дней (по желанию с выгрузкой в S3).

Для локальной разработки есть `docker-compose.dev.yml` только с Postgres.

### 12.2. CI/CD (GitHub Actions)

1. На PR: `lint`, `typecheck`, юнит-тесты, интеграционные тесты (Postgres как service container), `build`.
2. На push в `main`: сборка образов `app` и `migrate` → push в GHCR → SSH на VPS → `docker compose pull` → `docker compose run --rm migrate` → `docker compose up -d`.
3. E2E (Playwright) добавляются в пайплайн на этапе полировки.

### 12.3. Переменные окружения


## 13. Демо-данные и сброс

Генератор демо-данных лежит в `src/server/demo/`: `catalog.ts` (прайс, мастера, графики, справочники), `generate.ts` (чистая функция, строит все строки), `reset.ts` (запись в БД). Сброс вызывают `prisma/seed.ts` (`npm run db:seed`) и `POST /api/cron/demo-reset`. Клиент БД передаётся параметром, поэтому модуль работает и в сиде через tsx.

Создаётся:
- пользователи `owner@demo.ru`, `admin@demo.ru`, `master@demo.ru` с фиксированными ID, пароли из env;
- 4 мастера с разными графиками и ценами (у топ-барбера нестандартные длительности), двумя акциями, отпуском в будущем, больничным в прошлом и разовым перерывом;
- 4 категории и 10 услуг (стрижки, борода, комплексы, окрашивание);
- 3 промокода, один из них уже истёк;
- 400 клиентов с реалистичными именами, тегами, заметками, у части постоянная скидка. Клиенты появляются постепенно, часть перестаёт ходить и становится «спящей»;
- около 1300 записей за последние 90 дней и на 14 дней вперёд со смесью статусов, примерно 8% неявок, оплатами (часть визитов не оплачена) и скидками.

Записи раскладываются последовательно внутри рабочих интервалов мастера с учётом буфера и отпусков. Поэтому они не нарушают график и constraint, и генератору не нужен `getAvailableSlots`. Это проверяют юнит-тесты генератора. Цены и скидки записей генератор считает той же `calculatePricing`, что и запись с сайта: демо-данные не могут разойтись с правилами раздела 7.3.

Фото мастеров для демо сгенерированы Codex (навык `codex-image`) и лежат в `prisma/seed-assets/masters/` вместе с манифестом промптов. Они кодируются из PNG-оригинала скриптом `scripts/encode-seed-photo.ts` так же, как загрузка в CRM, а в имени файла есть хэш содержимого: `/uploads` раздаётся как immutable, и замена фото под прежним именем осталась бы незамеченной. Сброс копирует их в `UPLOADS_DIR/masters/` и удаляет файлы, на которые никто не ссылается, — так исчезают фото, загруженные посетителями.

Правила:
- Генератор **детерминированный** (фиксированный seed генератора). Даты строятся от начала текущего дня в таймзоне салона, поэтому демо не «стареет»: всегда есть и прошлые визиты, и будущие записи.
- Раскладка записей зависит только от даты. От времени сброса зависят лишь статусы сегодняшних записей (прошедшие завершены, будущие ждут).
- Сброс работает только при `DEMO_MODE=true` и выполняется в одной транзакции: очистка бизнес-таблиц и генерация заново. Пока транзакция идёт, читатели видят старые данные.
- Демо-пользователи пересоздаются с теми же ID и паролями, поэтому их сессии переживают сброс. Пользователи, созданные посетителями, удаляются вместе с сессиями.
- Загруженные файлы, на которые после сброса никто не ссылается, удаляются из `uploads`.

## 14. Тестирование

- **Юнит (Vitest)**: `getAvailableSlots` (все кейсы из 6.5, плюс переход на летнее время и сетка в поясе UTC+5:30), `calculatePricing` (акции, промокоды, скидка клиента, ручная скидка, выбор лучшей, округление, нулевая цена), нормализация и маскирование телефона, функции метрик на фиксированных данных. Тесты расчётов пишутся до кода и проверяются «мутантами»: если сломать правило в реализации, хотя бы один тест должен упасть.
- **Интеграционные (Vitest + тестовая БД)**: constraint `booking_no_overlap`, включая гонку двух параллельных записей на один слот (ровно одна успешна); слоты на демо-данных против constraint — каждое предложенное время база принимает (вставка с откатом); `createWebsiteBooking` — снимок цены, «одна активная запись на телефон» (и при параллельных запросах), «любой мастер» при занятом первом, изменившаяся цена, лимит промокода под гонкой; отмена по токену; outbox — повтор после ошибки и одна отправка при двух параллельных доставках; перенос с пересечением; сброс демо дважды подряд даёт одинаковый результат.
  - Запускаются отдельно: `npm run test:integration`. Нужен Postgres из `docker-compose.dev.yml`.
  - Работают с отдельной БД `TEST_DATABASE_URL`. Она создаётся автоматически, к ней применяются миграции. Тесты откажутся запускаться на базе, имя которой не оканчивается на `_test`.
- **E2E (Playwright)**: полный путь записи с телефона; отмена по ссылке; вход в админку и смена статуса.

## 15. Этапы работ

Каждый этап делается в отдельной ветке, заканчивается зелёными `lint`, `typecheck` и тестами, коммитом и **остановкой для ревью**.

1. **Каркас.** Next.js + TS strict, Tailwind, shadcn/ui, Prisma, docker-compose с Postgres для разработки, `.env.example`, валидация env, ESLint/Prettier, Vitest.
2. **Схема БД.** `schema.prisma`, миграции, constraint из 5.3, генератор демо-данных и сид.
3. **Авторизация.** Логин, `requireRole` и проверка владения, защищённый layout админки, ограничения режима демо.
4. **Справочники.** CRUD категорий, услуг, мастеров (цены, фото, акции), графика, отпусков, промокодов, пользователей.
5. **Расчёты.** `getAvailableSlots` и `calculatePricing` + юнит-тесты (сначала тесты).
6. **Запись с сайта.** Мастер записи, `createBooking`, страница записи с отменой и .ics, outbox и Telegram-уведомления.
7. **Админка записей.** Экран «Сегодня», календарь, список, смена статусов, ручная запись, перенос, длительность, ручные цены и скидки, оплаты, удаление.
8. **CRM.** Список и карточка клиента, теги, заметки, постоянная скидка.
9. **Аналитика.** Метрики из 8.3, вид мастера, графики.
10. **Публичный сайт.** Главная, услуги, мастера, политика ПДн, баннер демо, ссылка на канал, SEO. Главная, политика ПДн и плашка демо в подвале сделаны раньше, по просьбе пользователя (ветка `stage-10-landing`).
11. **Деплой.** Dockerfile, compose, Caddy, cron (уведомления, сброс демо), бэкапы, GitHub Actions, домен.
12. **Полировка.** E2E-тесты, Lighthouse, README со скриншотами и архитектурой.

## 16. Принятые решения

Открытые вопросы первой версии документа закрыты 2026-10-27:

- Запись с сайта создаётся в статусе `PENDING`, подтверждает мастер или админ.
- Мастер видит выручку только по своим записям.
- Фото мастеров хранятся в Docker volume, раздаются через Caddy.
- Проект чисто демонстрационный: публичная часть открыта всем, закрытая доступна по выданным паролям, данные сбрасываются каждый час.
- Уведомления идут в публичный Telegram-канал с маскированными телефонами.
- Телефоны принимаются любых стран.
- Исходный черновик схемы взят за основу. Отличия: теги и заметки вынесены в отдельные таблицы (нужны цвет тега, автор и время заметки); `telegramChatId` и `marketingOptIn` у клиента убраны до фазы 2 (напоминания и рассылки).

## 17. Правила для работы с кодом

- TypeScript strict, без `any`.
- Бизнес-логика в `src/server/`, Zod-схемы в `src/lib/validation/`, компоненты без прямых запросов к Prisma.
- Деньги только через `lib/money.ts`, даты только через `lib/time.ts`.
- Новая логика расчётов пишется вместе с тестами.
- Изменения схемы БД делаются только через миграции Prisma. При изменении модели обновлять раздел 5 этого документа.
- Интерфейс и сообщения пользователю на русском, код и названия сущностей на английском.
